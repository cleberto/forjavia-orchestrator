Visão geral: [README](../README.md).\n\n## Hoje e alvo\n\n- **CURRENT (experimental, local):** relay governado local no perfil Codex→Claude, com resultado estruturado e adjudicação; veja [13-governed-bridge.md](13-governed-bridge.md). É um perfil de uso, não a arquitetura.\n- **PLANNED:** schema do Structured State, integração com Spec Kit, TLC Spec-Driven e Understand Anything, Integrated Engineering Graph, Forjavia UI, autonomia integrada e transporte via GitHub/cloud (não comprovado).\n\nO restante deste documento descreve o alvo. Nada passa a CURRENT sem evidência verificada.\n\n## Responsabilidades\n\n| Componente | Responsabilidade |\n|---|---|\n| Forjavia | único Control Plane: state, governance, authority, permissions, provenance, invalidation, risk routing, context e integração |\n| Structured State | única fonte da verdade, versionada no repositório |\n| Forjavia UI | projeção do Structured State; interface humana principal futura |\n| GitHub | distribuição e histórico do repositório; não é fonte da verdade nem segunda área de trabalho |\n| Spec Kit, TLC Spec-Driven, Understand Anything | providers de capacidade |\n| Claude, Codex e outros | providers de execução substituíveis |\n\n## Três planos\n\n| Plano | Quem | Responsabilidade |\n|---|---|---|\n| Control Plane | Forjavia | state, governance, authority, permissions, risk routing, Context Compiler, Legacy Reconciliation, Parallel Scheduler, evidence/provenance e integração |\n| Provider Plane | Spec Kit (ciclo SDD), TLC Spec-Driven (mecânicas de qualidade e verificação), Understand Anything (Code Intelligence) | capacidades especializadas; providers não governam o sistema |\n| Execution Plane | Claude Code, Codex, agentes futuros, scripts, testes, CI e demais executores/Sensors | execução e sensores substituíveis |\n\nA integração com os providers de capacidade está planejada. Nenhum está integrado hoje.\n\n## Papéis e providers\n\n`ROLE != PROVIDER`. Papéis (por exemplo orchestrator, executor, verifier) são configuráveis e separados de quem os executa:\n\n- um provider pode ocupar vários papéis;\n- um único provider simples pode operar o fluxo;\n- vários providers podem dividir os papéis.\n\nO Forjavia não exige multi-agent. Regras como `author != verifier` continuam valendo e a configuração de papéis precisa satisfazê-las. O perfil local Codex→Claude é uma configuração experimental, não um modelo obrigatório.\n\n## Fluxo\n\nUsuário → Forjavia Front Door/UI → Structured State → Risk Router → Spec Kit/TLC/Understand Anything → Executor/Sensors/Verifier → Evidence/Converge → State Builder → Forjavia UI/Docs.\n\n## Autonomia governada (PLANNED)\n\nUm pedido do usuário pode conduzir um workflow de várias tarefas (`USER_INTENT_CAN_DRIVE_MULTI_TASK_WORKFLOW`), e o Forjavia continua sem comando humano a cada tarefa enquanto houver autoridade (`AUTO_CONTINUE_WHILE_AUTHORIZED`):\n\ncontexto → risco → spec quando necessária → plano → tasks, dependências e ordenação → execução → teste → reparo → revalidação → verificação → convergência.\n\nO ciclo para em: entrega; `OWNER_REQUIRED` real; `AUTHORITY_BLOCK`; bloqueio irrecuperável. Autonomia significa continuar dentro da autoridade, nunca ampliá-la. Ainda não está implementado de forma integrada.\n\n## Princípios\n\n- procedimento → script; julgamento → LLM; regra bloqueante → enforcement.\n- O risco prevalece sobre o tamanho do diff.\n- Sem duplicar source of truth.\n- Contexto compilado, não acumulado.\n- Falha destilada, não despejada.\n- Paralelismo só com dependências, isolamento e budget comprovados.\n- Convergência da integração antes de adotar nova tecnologia relevante.\n\n## Structured State e source of truth\n\n- O Structured State versionado no repositório é a única fonte da verdade.\n- `CLAUDE.md`, `AGENTS.md`, prompts e payloads de SDK são projeções compiladas, nunca fonte da verdade.\n- Fontes legadas (issue trackers, boards, documentos, planilhas) podem ser lidas durante o bootstrap, mas não viram espelho permanente nem segunda área de trabalho.\n- A evidência fica ligada à revisão; pareceres perdem validade quando seus inputs mudam.\n\n## Context Compiler\n\nCapability do Control Plane, sempre presente como boundary de contexto, com profundidade proporcional ao risco (LIGHT, STANDARD, CRITICAL). Produz o menor contexto suficiente para cada papel; não carrega providers inteiros, histórico completo nem lessons não relacionadas.\n\n## Capacidades condicionais\n\n- **Lesson Distiller:** só entra após falha ou finding relevante, retrabalho material, blocker recorrente ou escaped defect. Segue o caminho falha/evidência → causa raiz → lesson fundamentada → regra candidata → Sensor/validator/teste/enforcement quando automatizável. PASS limpo não cria lesson.\n- **Parallel Scheduler:** subordinado ao Orchestrator; paraleliza só quando o grafo de dependências e conflitos, o isolamento de escrita e os budgets permitem. Escrita concorrente não isolada na mesma árvore é proibida por padrão.\n- **Existing Project Bootstrap / Legacy Reconciliation:** confronta código, documentação, backlog, testes e evidências antes de promover qualquer estado a canônico. Nenhuma fonte legada vira authority automaticamente; após a reconciliação, a dependência operacional dela é encerrada.\n\n## Integrated Engineering Graph\n\nRequirement ↔ Task ↔ Code ↔ Dependency ↔ Test ↔ Evidence ↔ Commit.\n\nO Work Graph do Forjavia e o Code Graph do Understand Anything serão ligados por adapters versionados. A inferência semântica é advisory; somente fatos estruturais verificáveis podem ser candidatos a evidência.\n\n## Forjavia UI (futura)\n\nA Forjavia UI será a única interface humana principal, construída a partir do dashboard do Understand Anything e evoluída com identidade própria e módulos operacionais (Overview, Work, Specs & Requirements, Tasks/Waves, Tests & Sensors, Evidence & Provenance, Decisions/Questions, Releases, Architecture, Governance). Não haverá segunda UI operacional.\n\nRegra: UI = projeção; Structured State do repositório = verdade. A UI ainda não existe.\n\n## Governed Agent Relay\n\nFluxo entre papéis: Orchestrator → governed runner → Executor → resultado estruturado/evidência → Orchestrator, com adjudicação `CONTINUE / RETRY / OWNER_REQUIRED / STOP`. O fluxo não depende de transporte manual de prompts ou resultados pela pessoa usuária ou por quem detém autoridade. Hoje existe apenas como bridge local experimental no perfil Codex→Claude; o transporte via GitHub/cloud não foi comprovado e o gate de cutover permanece aberto.\n\n## Non-negotiables\n\nimplementation != proof; proof != authority to close; author != verifier; procedure → script, judgment → LLM, blocking rule → enforcement; semantic graph inference is advisory; risk dominates diff size; no source-of-truth duplication; no second operational UI; no permanent legacy tracker dependency; context is compiled, not accumulated; failure memory is promoted, not dumped; parallelism is dependency-driven; integration convergence precedes new major technology adoption; the flow does not depend on manual relay of prompts or results by the user or by the authority holder.\n"}
